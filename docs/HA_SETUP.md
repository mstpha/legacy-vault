# Legacy Vault: high availability setup

Two backends, two Supabase projects, one sync worker. Everything runs locally on separate ports.

```
                        GET /health every 5 s (both)
   legacy-vault-app ───────────────────────────────┐
   (src/api/client.js:                             │
    health-aware routing, retries, failover,       │
    Idempotency-Key)                               │
        │ primary first                            │ fail over
        ▼                                          ▼
 ┌──────────────────────┐                ┌───────────────────────────────┐
 │ legacy-vault-backend │                │ legacy-vault-backend-backup   │
 │ :4000  role=primary  │                │ :4001  role=backup            │
 │ only ever uses A     │                │ DB router: A_ACTIVE ⇄ B_ACTIVE│
 │ /health 503 if A down│                │            ⇄ DRAINING         │
 └──────────┬───────────┘                └──────┬─────────────────┬──────┘
            │                                   │ (A_ACTIVE)      │ (B_ACTIVE / DRAINING)
            ▼                                   ▼                 ▼
     ┌─────────────┐   ha.change_log  A→B  ┌─────────────┐
     │ Supabase A  │ ─────────────────────▶│ Supabase B  │  warm standby
     │ (authority) │ ◀───────────────────── │             │
     └─────────────┘   B outbox  B→A       └─────────────┘
                 ▲   (replayed first)         ▲
                 └──── sync worker :4100 ─────┘   (npm run sync:worker in the backup folder)
```

## 1. Failure modes

| Case | What happens | Sync involved |
|---|---|---|
| **(a) Primary process crashes, A healthy** | The app's request fails (network error) → it marks primary down, retries ×2, fails over to the backup. The backup is `A_ACTIVE`, so it serves straight from A. When primary comes back, the app fails back after 3 healthy probes. | None. The backup writes to A, and A→B keeps running as usual. |
| **(b) A unreachable** | Primary `/health` → 503 and API calls → 503 `DB_UNAVAILABLE`, so the app fails over. After 3 failed checks (`A_FAIL_THRESHOLD`) the backup flips to `B_ACTIVE`, and B's triggers journal every write in B's outbox. When A is back for 5 checks (`A_RECOVER_THRESHOLD`) the backup moves to `DRAINING` and replays the outbox to A. For the final drain it pauses writes (503 + `Retry-After`; reads keep working), drains to 0, flips to `A_ACTIVE`, then runs sync-check. The app fails back only when the backup reports `A_ACTIVE` with `outboxPending == 0`. | B→A replay first, then A→B resumes. |
| **(c) A flapping** | Any success resets the failure streak and any failure resets the success streak. A→B needs 3 failures in a row, and B→A needs 5 successes in a row plus a finished drain, so an A that alternates up/down never triggers a transition. Requests that hit A during a down blip get a 503, and the app retries or fails over. A failure during `DRAINING` sends the backup back to `B_ACTIVE` and the drain resumes later. | — |
| Backup's B dies while A is back but not yet 5× healthy | Forced flip to `A_ACTIVE` (`b_unreachable_forced`). Whatever is left in B's outbox replays (LWW) when B returns. | Deferred |

## 2. One-time setup: clone A into B

> **Order matters:** install capture on A *before* copying data, and on B *after*. That makes the copy zero-downtime and lossless: everything A writes during the copy is in A's change log and gets replayed onto B.

### 2.1 Create B
Create a new Supabase project in the **same region** as A (keeps clock skew and latency low). Save its DB password, `Project URL`, `anon` and `service_role` keys, plus both connection strings (transaction pooler on 6543, direct on 5432).

### 2.2 Schema, enums, indexes, constraints → B
The schema is fully Prisma-managed, so replay the same migrations:

```powershell
cd legacy-vault-backend-backup
$env:DATABASE_URL = "<B pooler url>"; $env:DIRECT_URL = "<B direct url>"
npx prisma migrate deploy        # all migrations, enums, indexes, FKs
Remove-Item Env:DATABASE_URL, Env:DIRECT_URL
```

Equivalent with the Supabase CLI (also picks up anything created by hand on A):

```bash
supabase db dump --db-url "$A_DIRECT_URL" -f schema.sql            # schema only (public + private, functions, triggers, RLS)
supabase db dump --db-url "$A_DIRECT_URL" --role-only -f roles.sql  # custom roles, if any
psql "$B_DIRECT_URL" -f roles.sql -f schema.sql
```

Then, on B, in the SQL editor or with psql:

1. `legacy-vault-backend/prisma/rls-policies.sql`: RLS, column grants, `private.*` helper functions, the append-only audit trigger.
2. Extensions: none beyond Supabase defaults (ids are generated by Prisma, and hashing happens in Node). Check with `select extname from pg_extension;` on both projects.

### 2.3 Install change capture on A (no downtime, the primary keeps serving)
```bash
psql "$A_DIRECT_URL" -f ha/sql/001_ha_schema.sql -c "select ha.set_node('A');"
```
From here on, every write on A lands in `ha.change_log` as `pending`.

### 2.4 Initial data copy A → B
```bash
# public data only; _prisma_migrations already exists on B from migrate deploy
pg_dump "$A_DIRECT_URL" --data-only --schema=public --exclude-table=public._prisma_migrations \
        --no-owner --no-privileges -f data.sql
psql "$B_DIRECT_URL" -v ON_ERROR_STOP=1 -f data.sql
```
(`supabase db dump --data-only --use-copy` also works.) `pg_dump` orders tables by FK dependency and restores the `audit_logs.seq` sequence value. B has no capture triggers yet, so the restore isn't journaled.

### 2.5 Install capture on B
```bash
psql "$B_DIRECT_URL" -f ha/sql/001_ha_schema.sql -c "select ha.set_node('B');" -f ha/sql/002_b_only.sql
```
`002_b_only.sql` lets the sync process (and only the sync process) overwrite B's mirror of the audit chain (see 3.6). Re-run it every time you re-run `rls-policies.sql` on B.

### 2.6 Storage
1. On B, create the bucket **`capsule-files`, private, no policies** (Dashboard → Storage, or `insert into storage.buckets (id, name, public) values ('capsule-files','capsule-files',false);`).
2. Copy the existing objects: `npm run sync:check` (in the backup folder). Its storage pass copies every object referenced by `capsule_files` that is missing on B. After that, the worker copies each new object along with its `capsule_files` row.

### 2.7 Catch up and verify
Start the worker (`.\scripts\ha.ps1 worker`). It replays whatever A journaled during the copy. Then:
```powershell
.\scripts\ha.ps1 check -DryRun     # expect "clean": true (exit code 0)
```

### 2.8 Auth users
The app **does not use Supabase Auth**. Identities are rows in `public.users` (bcrypt `passwordHash`, `mfaSecret`), and sessions are JWTs signed with `JWT_ACCESS_SECRET` plus hashed opaque refresh tokens in `public.refresh_tokens`. All of that is ordinary table data, so the copy above already clones every user with **identical ids and password hashes**, and the sync keeps it current.
- The backup validates A-issued tokens **locally** (`jsonwebtoken.verify`, no network) because it has the **same `JWT_ACCESS_SECRET`**. That works whichever DB is active.
- The backend connects as `postgres` (Prisma) / `service_role` (Storage), which bypasses RLS, and enforces user scoping itself (`requireAuth`, ownership checks in the services). No code path builds a user-JWT-scoped Supabase client, so **B's JWT settings are irrelevant**.
- If you ever add user-JWT-scoped clients: B would reject A-signed tokens. The practical fix is to make B trust A's key. On legacy projects, set B's JWT secret to A's (Settings → API → JWT secret; this rotates B's anon/service keys). On projects with JWT signing keys, import A's signing key into B as a standby key. Cloning `auth.users`/`auth.identities` would also need a dump of the `auth` schema (allowed for data via `pg_dump --schema=auth --data-only` on most projects, but the Admin API is the supported route). None of this is needed today.

### 2.9 What can't be cloned automatically (manual dashboard work on B)
- Storage bucket creation and settings (size limits, MIME restrictions). Objects are copied by sync-check and the worker.
- Project settings: Auth providers/SMTP/redirect URLs (unused today), API exposed schemas, network restrictions/SSL enforcement, pooler mode and pool size, PITR/backups, custom domains, log drains.
- Edge Functions and their secrets: **none in this repo**. If added: `supabase functions deploy --project-ref <B>` and `supabase secrets set --project-ref <B>`.
- Realtime publications: **not used**. If added, mirror `alter publication supabase_realtime add table ...` on B.
- Database webhooks, cron jobs (pg_cron), Vault secrets: none today. They would need re-creating on B.

## 3. Sync design

### 3.1 Why change log + triggers + external worker
| Option | Verdict on hosted Supabase |
|---|---|
| Logical replication / subscriptions | No superuser, so no `CREATE SUBSCRIPTION` across projects. It's also one-way: B→A replay after an outage would need a second, reversed setup and conflict handling we don't control. |
| Dual-write from the backend | Every code path (Prisma calls, raw SQL in the sweep, transactions) would need to write twice. A crash between the two writes diverges silently, and there's no journal to replay. |
| **Triggers → `ha.change_log` + worker** | Captures **every** write regardless of code path (Prisma, `$queryRaw`, cascades, manual SQL). Plain SQL, so it works on hosted projects. Gives a durable, ordered, resumable journal in both directions. Costs: async, so there is lag (RPO = lag, usually ~1 s); 2 extra inserts per written row; and a worker to run. |

### 3.2 Objects (in schema `ha`, outside Prisma's `public`, so there is no migration drift)
- `ha.change_log`: on A, the A→B stream; on B, the **outbox**. Columns: `op, schema_name, table_name, row_id, payload (full row), changed_at, origin, status (pending|applied|skipped|conflict), attempts, last_error`.
- `ha.row_versions`: per row `updated_at` (time of last change, deletes included) and `deleted_at` (**tombstone**). This is the LWW clock.
- `ha.idempotency_keys`: part of the sync set (has the capture trigger).
- `ha.sync_audit`: every conflict and every sync-check fix, plus one `run_summary` per sync-check run.
- `ha.capture()` (trigger on every synced table), `ha.apply_change()` (LWW upsert/delete), `ha.exec_unjournaled()`, `ha.row_hash()`.

**Which tables need `updated_at`/`deleted_at`:** LWW needs both on every synced table. These have no `updatedAt` at all: `refresh_tokens, capsule_files, capsule_guarantors, capsule_beneficiaries, validations, audit_logs, notifications`. `capsule_key_shares.updatedAt` is a default only, and `users/capsules/role_permissions.updatedAt` is set by the Prisma client, not the DB, so raw-SQL updates can skip it. None of them has `deleted_at`. Instead of adding columns to 11 tables (which means a Prisma migration plus a `deletedAt IS NULL` filter in every existing query for soft deletes), the trigger records both in `ha.row_versions` with the DB's own clock. Hard deletes stay hard, and the tombstone outlives the row. The migration for both projects is `ha/sql/001_ha_schema.sql`.

### 3.3 Flow
- **A → B (warm standby):** A's triggers journal everything. Each tick, the worker leases pending rows (`FOR UPDATE SKIP LOCKED`), applies them to B in id order with `ha.apply_change`, then marks them. This runs whichever backend is serving, and **only while B's outbox is empty**.
- **B → A:** in `B_ACTIVE`, B's triggers journal into B's outbox. A→B is naturally paused while A is down, and stays paused while B has pending rows. On recovery, the worker *and* the backup's router (during `DRAINING`) replay B's outbox to A **before** A→B resumes. Both can run at once thanks to `SKIP LOCKED`.
- **Loop prevention:** `ha.apply_change` sets the transaction-local GUC `ha.applying=on`, and `ha.capture()` ignores writes made with it. Replayed changes are never re-journaled, so they never bounce back.
- **Resumable/idempotent:** the `status` column is the checkpoint. A crash after applying but before marking just re-applies (LWW upsert, same result). Unreachable project → the batch is rolled back and that direction backs off exponentially (1 s → 30 s). A data error (unique email already taken on the other side, an FK to a row deleted there) is retried `SYNC_MAX_ATTEMPTS` times, then marked `conflict` and logged to `ha.sync_audit`, so one bad row can't wedge the stream.
- **Status:** `GET http://127.0.0.1:4100/status` gives pending counts and errors per direction. The backup's `/health` reports `outboxPending` (read from B directly, the source of truth) and embeds the worker status when `SYNC_WORKER_STATUS_URL` is set.

### 3.4 Conflict rule
Last write wins on `ha.row_versions.updated_at` (DB `clock_timestamp()` at write time, kept from the origin when replayed). Tombstones take part: a delete newer than an update wins, and an update newer than a delete resurrects the row. Equal timestamps re-apply (same change seen twice). With no version on either side, **A is authoritative**.

### 3.5 Partial outage (primary still reaches A while the backup can't)
Both sides take writes. The primary's writes are journaled on A, and the backup's on B. The worker (which may reach both) replays B→A, then A→B. Both projects converge **per row** to the latest write. Two users editing the same row on different sides: the later one wins, and the earlier one is overwritten (recorded as `skipped` in the change log). Inserts never collide (UUIDs). Unique-key collisions (the same email registered on both sides) become `conflict` rows for manual review. Hysteresis keeps this window as short as A's real reachability allows.

### 3.6 Special case: the audit hash chain
`audit_logs` is append-only (trigger) and hash-chained (`seq`, `prevHash`, `hash`). Copying B's outage entries verbatim to A would fork A's chain and collide on `seq`. Instead, the worker **re-chains** each B entry onto A: it keeps the same id, content, and `createdAt`, gets a new `seq`, and has its `prevHash`/`hash` recomputed under A's chain advisory lock. That insert is journaled on A, so the re-chained version flows back to B. There, `002_b_only.sql` allows `ha.apply_change` to replace B's outage-era copy (only when `ha.applying=on`). A's audit log is never updated or deleted by any HA component, and `GET /api/audit/verify` stays valid on A.

## 4. sync-check (reconciliation)
`npm run sync:check` (auto-fix) · `npm run sync:check:dry` (report only) · `node src/ha/syncCheck.js --table=users,capsules --no-storage`
- Per table: row counts, max `row_versions.updated_at`, then a chunked merge-walk of `(id, md5(to_jsonb(row)))` on both sides → **missing in B, extra in B, diverged**.
- Rows pending in a change log or written within `SYNC_CHECK_GRACE_MS` count as in flight and are skipped (reported as `inFlightSkipped`).
- Fixes follow the conflict rule. Upserts go in FK order and deletes in reverse. `audit_logs`: A wins, and B-only entries are re-chained onto A. Each fix is logged to `ha.sync_audit` on A.
- **Storage:** every `capsule_files.storagePath` must exist in both buckets, and missing objects are copied from the side that has them. *Not covered:* orphan objects with no row on either side (that would need a full bucket scan; they are harmless ciphertext), and object *content* drift (paths are immutable: `<capsule>/<ts>-<random>-<name>`, uploaded with `upsert:false`).
- **Auth users:** covered as the `users` table (there is no Supabase Auth data). `auth.*` schema: excluded, unused.
- **Excluded:** `_prisma_migrations` (migrated on both), `ha.*` bookkeeping.
- Runs on a schedule in the worker (`SYNC_CHECK_INTERVAL_MS`, default 1 h) and automatically on `DRAINING → A_ACTIVE` (`SYNC_CHECK_ON_CUTOVER`).
- An unreachable project → `skipped` in the report, exit code 3, no crash. Exit codes: 0 clean · 2 differences (fixed, or found in dry-run) · 3 skipped · 1 error.

## 5. Running it
Prerequisites: `npm install` and `npx prisma generate` in **both** backend folders; `.env` filled from each `.env.example`; Redis running.
```powershell
.\scripts\ha.ps1 all        # primary :4000, backup :4001, worker :4100, each in its own window
.\scripts\ha.ps1 status     # /health of both + worker status
.\scripts\ha.ps1 primary    # or backup / worker, individually
```
App: `legacy-vault-app/.env` with `EXPO_PUBLIC_PRIMARY_API_URL` and `EXPO_PUBLIC_BACKUP_API_URL` (use the LAN IP for a phone). Restart Expo with `-c` after changing it.

## 6. Hosted-Supabase limits that affect this design
- **Free tier pausing:** inactive free projects get paused after ~7 days. B is a standby, and the worker's polling may not count as activity. Use a paid plan for B, or at least check it weekly. A paused B means no failover.
- **Connections:** each Prisma client opens its own pool. Processes: primary (A) + backup (A and B) + worker (A and B). Keep `connection_limit=5` on the pooler URLs, use the **transaction pooler** (6543, `pgbouncer=true`), and use direct 5432 only for migrations/dumps. The free tier allows about 60 direct / 200 pooled connections.
- **DB size:** `change_log.payload` holds full rows, and `capsules.encryptedContent` can be ~10 MB as hex JSON, so each capsule update journals that much. Applied rows are purged after `SYNC_CHANGELOG_RETENTION_DAYS` (3). On the 500 MB free tier, lower it if needed.
- **Storage:** API rate limits and egress apply to the worker's copy traffic (download from one project, upload to the other). sync-check does 2 `list` calls per file.
- **Long transactions:** a worker batch holds a transaction on the source while it writes to the target (`SYNC_LEASE_TIMEOUT_MS`, 120 s). Lower `SYNC_BATCH_SIZE` if the pooler kills long transactions.
- **Clock:** LWW uses each project's DB clock (NTP-synced managed hosts, ms-level skew). Keep A and B in the same region.

## 7. Manual test plan
Prep: the three processes running, and the app on primary (no banner). Keep `.\scripts\ha.ps1 status` handy.

**T1. Primary crash, A healthy**
1. Close the "LV primary" window.
2. In the app, do a read and a write (create a capsule). Expected: the request succeeds after a short delay, and the banner shows **"Backup server"**.
3. `ha.ps1 status`: backup `db.state=A_ACTIVE`, `outboxPending=0`; worker `bToA.pending=0`. The write is in A (the primary DB) and reaches B through A→B.
4. Restart the primary (`ha.ps1 primary`). Within ~3 probes (≈15 s) the banner disappears and requests go to :4000 again.

**T2. A unreachable**
1. In **both** backends' `.env`, break A: e.g. `DATABASE_URL=...@127.0.0.1:1/...` (backup: same variable). Restart both. *(Alternative that keeps the config: block the A pooler host in the Windows firewall or `hosts`.)*
2. Primary `GET /health` → **503** `{role:"primary", db:{status:"down"}}`. The app fails over.
3. Backup `/health`: `state=B_ACTIVE`, `active=B`, `a=down` (immediately at boot, or after 3 checks if it was already running). Banner: **"Backup server, degraded: backup database"**.
4. Write data: create a capsule, attach a file, add a guarantor. Backup `outboxPending` rises (`select count(*) from ha.change_log where status='pending'` on B).
5. Restore A: fix the backup's `.env` and restart it, or unblock A if you used the firewall (then the running router sees A come back).
   - With the firewall method, watch the backup log: `ha_db_transition B_ACTIVE→DRAINING` after 5 good checks, then `ha_final_drain_started`, then `DRAINING→A_ACTIVE (drain_complete)`, then `sync_check_done clean:true`.
   - With the restart method, the backup sees a non-empty outbox at boot and starts in `DRAINING` (`outbox_pending_at_boot`), still serving from B. It flips to `A_ACTIVE` after 5 good checks and the final drain. The worker drains in parallel, so check that it shows `bToA.pending=0`.
6. On A: the new capsule, file row, and guarantor exist; the file downloads; `GET /api/audit/verify` → `valid:true`.
7. `ha.ps1 check -DryRun` → `clean: true`.
8. Fix the primary's `.env`, restart it. The app fails back only after the backup reports `A_ACTIVE` + `outboxPending 0` and the primary has had 3 healthy probes.

**T3. A flapping**
Use the firewall method and toggle the block every ~3 s (less than `A_FAIL_THRESHOLD × A_CHECK_INTERVAL_MS` = 6 s). Expected: the backup stays `A_ACTIVE`. `transitions` in `/health` stays empty, and logs show `ha_db_check_failed` without `ha_db_transition`. Then hold the block for 10 s: one transition to `B_ACTIVE`. Toggle again: it stays in `B_ACTIVE` (5 successes in a row never happen).

**T4. Retry / idempotency**
1. Same key, same server:
   ```bash
   curl -X POST localhost:4000/api/capsules -H "Authorization: Bearer $T" -H "Idempotency-Key: t4-1" -H "Content-Type: application/json" -d '{...}'
   ```
   Run it twice. The second call returns the same body with `Idempotent-Replayed: true`, and exactly one capsule exists.
2. Across servers: send the same command to :4001. Same response, no duplicate (the key reached B/A through the sync set).
3. Timeout plus retry in the app: set `EXPO_PUBLIC_REQUEST_TIMEOUT_MS=50` temporarily and create a capsule. The client times out, retries with the same key, and only one capsule is created.
4. Across a DB switch: during T2 step 4, create with key `t4-2` on the backup (B). After the drain, retry `t4-2` on the primary (A) → replayed, no duplicate.
5. Same key with a different body → **422**.

## 8. Known limitations / risks
- **RPO = replication lag.** A write acknowledged by A in the ~1 s before A dies, and not yet copied to B, is missing from B during the outage. It's not lost: it's still in A's change log and replays to B on recovery (LWW). An idempotency key in that window may not be visible on B, so a retry could execute twice.
- **LWW is per row, not per field or transaction.** Concurrent edits on both sides during a partial outage keep the later row. Multi-row invariants (e.g. `validationsReceived` vs `validations` rows) can disagree temporarily, and sync-check cannot repair business invariants.
- **Unique-key collisions** (the same email registered on A and B during a split) end up as `conflict` rows and need a manual decision. Look in `ha.sync_audit`.
- `/api/auth/*` is excluded from idempotency (responses carry tokens). A `/auth/refresh` that timed out after the server rotated the token can log the user out on retry. That was already the case before HA.
- Router state is in memory. A restarted backup re-detects state from probes: `B_ACTIVE` if A is down, `DRAINING` if A is up but B's outbox is not empty, `A_ACTIVE` otherwise.
- Both backends share Redis (BullMQ inactivity sweep). Redis is a single point of failure for the sweep, not for the API.
- Rate-limit counters are in memory per process, so failover resets them.
- No NetInfo on native: "offline" is inferred from failed requests. AppState pause/resume works. Optional: `@react-native-community/netinfo` to pause probes while offline.
- Changes to `public` table structure must be migrated on **both** projects before deploying code (`npx prisma migrate deploy` against B). `ha.apply_change` copies whole rows by column name.
- TRUNCATE is not replicated (the capture trigger is row-level).
